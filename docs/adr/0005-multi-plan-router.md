# Multi-plan router with explicit time windows

**Date:** 2026-09-23
**Context:** Section 4.3 returned one SearchPlan and one Chroma where clause. ADR-0002 already requires two retrievals for the focus set, so a single plan cannot express that question. Direct vector ranking also cannot answer "next meeting", which needs the earliest calendar item after now, not the most similar one. Relative phrases other than today were undefined, and an invalid LLM response had no failure rule.
**Decision:** plan_query returns list[SearchPlan]. SearchPlan gains order_by: similarity (default, uses search) or time (earliest first, uses fetch). The router computes five UTC windows from the Reference Timestamp in code and gives the exact epochs to the model: today, yesterday, tomorrow, this week (Monday 00:00 through Sunday 23:59:59 UTC), and next meeting (calendar items with timestamp strictly after the Reference Timestamp, order_by time, limit 1). Any other phrase gets no time filter. The Reference Timestamp defaults to 2026-09-23T09:00:00Z and is overridden by FOUNDER_REFERENCE_TIME. Combined results are de-duplicated by id and sorted by timestamp. On timeout, HTTP 429, or invalid JSON the LLM call is retried once, then a Planning Failure is raised. The question is never answered with an unfiltered search.
**Consequences:** The single-SearchPlan output of section 4.3 is deleted. retrieve must run every plan. Next-meeting plans must not use cosine ranking. Tests that assume one plan for "focus today" or five email-level follow-ups are invalid. Missing OPENROUTER_API_KEY is a typed error, not a silent unfiltered search.
