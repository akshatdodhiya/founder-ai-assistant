# Jev classifies the founder question

**Date:** 2026-09-23
**Context:** ADR-0005 sent the founder question to a frontier model in JSON mode and asked that model to select time windows. That call adds latency and token cost, and an invalid JSON body forces a retry. The mock mail is already classified: requires_action and category are on the source record. Reclassifying those fields at ingest would make follow-up ids depend on a live model.
**Decision:** Jev classifies only the founder's question. One call to OpenRouter System One (`POST https://openrouter.ai/api/v1/systemone`, model `typesafe/jev-1.13`) asks two choice questions. Intent is one of `focus_today`, `follow_ups`, `repeated_customer`, `next_meeting`, or `general`. Window is one of `today`, `yesterday`, `tomorrow`, `this_week`, `next_meeting`, or `none`. Python builds every SearchPlan and every epoch from those labels. `focus_today` is always the ADR-0002 union and ignores a conflicting window. The winning label is used even at low confidence. The same `OPENROUTER_API_KEY` authorizes this call and later synthesis. Ingestion does not call Jev. Timeout or HTTP 429 retries once, then a Planning Failure is raised. A missing key is not retried. No unfiltered search is issued. The frontier chat model is not used by the router.
**Consequences:** This supersedes the ADR-0005 sentences that give epoch values to a model and that retry invalid JSON. ADR-0005 still holds for multi-plan retrieval, order_by, the five windows, the reference timestamp, and the ban on an unfiltered search. Section 4.3 no longer mentions JSON mode. Tests inject a fake classifier. No noul, audience, or issue-report field is added.
